# 计费方式兼容合同

本文件记录 `计费方式/` 截图所要求的计费能力。它不是仅供展示的清单：
`scripts/verify-core-compatibility.sh`、前端表达式测试和后端计费测试会在每次上游同步后验证这些能力。

逐模板的稳定 key、名称、功能、字段、编辑布局、管理端/客户端展示和真实结算说明统一登记在
[`billing-template-registry.md`](billing-template-registry.md)，机器可读合同位于
`extensions/frontend/model-prices/billing-template-registry.ts`。以后新增计费模板或高级媒体规则时，
必须同时更新这两份注册表和对应回归测试。

| 截图计费结构 | 可视化入口 | 实际计费数据 |
| --- | --- | --- |
| 按生成图片张数 | 图片分辨率模板或空白规则 | `output_images` |
| 请求开关使用不同单价 | 布尔请求选项模板 | `prompt_extend` 或自定义布尔字段 |
| 按生成数量分档 | 生成图片数量阶梯模板 | `output_images` / `count` |
| 音乐、语音按输出秒数 | 音频时长模板 | `seconds` 或 Token 表达式的 `aud_s` |
| TTS 按输入字符数 | 每万字符 TTS 模板 | `tts_input_characters` |
| 声音复刻按音色数 | 音色数量模板 | `count` |
| 输入长度分档 | 输入 Token 区间表达式模板 | `len` |
| 输入长度加思考开关 | 输入区间 + 思考输出表达式模板 | `len`、`param(enable_thinking)` |
| Qwen 单次输入长度 + 非思考/思考输出 | Qwen 输入区间与思考/非思考输出模板 | `len`、`param(enable_thinking)`；两个输出档位可独立编辑 |
| 共享输入价 + 思考/非思考输出 | 共享输入价 + 思考/非思考输出价模板 | `p` 只设置一次，两个 `c` 输出价分别设置；按 `param(enable_thinking)` 结算 |
| 两段输入长度 + 思考/非思考输出 | 两段输入长度 + 思考/非思考输出计价模板 | `len <= 256000` 分为短、长两档；每段的 `p` 和两种 `c` 可分别编辑 |
| 文本、图片、视频、音频分别计价 | 多模态表达式模板 | `p/c/img/img_o/vid/vid_o/ai/ao` |
| 纯文本/多模态文本/文本+音频三种输出 | Omni 输出模式表达式模板 | `img/ai/vid/ao` 条件分支 |
| 音频转写按秒 | 音频转写表达式模板 | `aud_s` |
| 视频分辨率乘输出时长 | 视频分辨率与时长模板 | `resolution`、`seconds` |
| 视频分辨率加有声/无声 | 视频分辨率、时长与音频开关模板 | `resolution`、`audio`、`seconds` |
| 视频标准/专业模式 | 视频模式与时长模板 | `mode`、`seconds` |
| 输入图片加输出视频 | 图片输入与视频输出模板 | `input_images`、`resolution`、`seconds` |
| 3D 任务类型与输出规格组合 | 任务类型与输出规格矩阵模板 | `task_type`、`output_spec` |

模板中的价格、分辨率、模式、档位和字段值均为可编辑初始值。管理员可以增加、删除或调整档位，
并非只能使用截图里的示例数值。任务渠道只有在渠道的 `billing_usage_schema` 提供对应字段时，
才会在运行时使用该字段结算；同步请求由图片、音频请求解析器生成对应 usage facts。

### Qwen3 Omni 三种输出价格模板兼容约束

原有 `omni-output-modes` 模板必须保留，已经使用该模板保存的价格表达式继续兼容。
新增的 `omni-shared-media-input-output-modes` 使用独立 key，功能与原模板一致，但管理端只提供
一个“图片/视频输入价格”输入框；修改该输入框时必须同时写入表达式中的 `img` 和 `vid`，
不能只修改页面展示值。

两种模板在管理端价格列表和客户端模型价格页中，都应按一行分组表格显示：输入单价包含文本、
音频、图片/视频，输出单价包含纯文本输出、多模态文本输出、文本+音频输出（仅音频计费）。
旧数据中的图片与视频输入价格如果不同，仍在同一个表格单元格内分别显示，不能丢弃任一价格。
管理端的折扣、加额和相对原厂价格差值继续沿用公共价格渲染逻辑。

共享输入编辑器只放在 `extensions/frontend/model-prices/visual-billing-document-editor.tsx`；
core 的可视化编辑器仅保留 `supportsPlatformVisualBillingDocumentEditor` 通用插槽。同步 upstream 后，
兼容性检查必须同时验证旧模板 key、新模板 key、平台编辑器插槽和单行价格表回归测试。

Qwen 模板的初始数字仅用于展示分支结构，不能直接当作截图中的人民币报价：
表达式系数以美元/百万 Token 存储。配置时应在可视化编辑器选择人民币，再按截图
录入 35b-a3b 的输入 1.8、两种输出各 10.8 元/百万 Token，或 27b 的输入 3、
两种输出各 18 元/百万 Token，编辑器会换算存储币种。截图仅提供 `0 < Token <= 256K` 的价格；模板为超过
256K 的请求保留了单独的可编辑档位，其初值只是占位，发布前应核对官方长上下文价格。
思考分支读取原始请求体中的布尔字段 `enable_thinking`；如果渠道使用其他请求字段，
需要在可视化条件中修改字段路径，否则会按非思考分支计费。
不需要按输入长度分档时，选择“共享输入价 + 思考/非思考输出价”模板；它只有三个价格输入框，
不会按 256K 划档。该模板同样以美元保存、通过编辑器币种设置换算；若渠道不用
`enable_thinking` 字段，应改用可编辑条件的通用模板并设置实际请求字段。

### 新增“共享输入价 + 三段输入长度 + 思考/非思考输出价”模板的约束

新增类似 `Three input ranges + thinking/non-thinking output prices` 的模板时，必须使用
独立的模板 key，不得覆盖或删除旧模板。新模板的每个输入长度档位只设置一次共用输入价格，
再分别设置思考和非思考输出价格；保存后必须序列化为现有 billing expression，由实际计费引擎
执行，不能只在价格页面展示。

模板编辑器需要满足以下约束：

1. 输入长度上限必须是可编辑参数，不能把截图中的 `32K`、`128K`、`256K` 或 `1M` 固定为代码常量。
   输入数字旁边应显示自动换算的可读单位（例如 `32000` 显示 `32K`，`1000000` 显示 `1M`）。
2. 最后一个无条件分支是默认/兜底档位，默认档位名称必须可以单独编辑；修改名称时要同时更新
   思考和非思考两个表达式分支，并保留 `thinking`、`non-thinking` 标识，以便前台合并显示和计费结果识别。
3. 每个档位都必须支持删除。删除时必须同时删除该档位的思考分支、非思考分支和共用输入价格；
   删除最后一个条件档位后，后续分支自动成为新的兜底档位。至少保留一个有效档位，不能生成空表达式。
4. 思考/非思考价格下方不需要暴露原始 tier 标签输入框。标签由编辑器自动维护，避免用户修改内部识别字段
   后导致前台无法合并同一档位。
5. 优惠、币种换算、前台价格展示、后台价格预览和实际计费必须共同覆盖共用输入价以及两种输出价。
   新增或重构模板后，应增加解析、可视化编辑、删除档位、实际计费和前台展示回归测试。

后续同步 upstream 时，先执行 `./scripts/assemble-extensions.sh` 和
`./scripts/verify-core-compatibility.sh`。兼容性检查必须登记模板 key、AST 的共用输入字段和
专用编辑器名称；检查失败时不得提交 core 子模块指针。

两段输入长度模板只用截图中的原价结构，不包含限时折扣。模板数值是演示值：
表达式以美元/百万 Token 存储，录入截图所示的人民币价格时先选择人民币显示币种。
第二段在计费表达式中作为最终分支。截图中的模型上限为 1M；超过模型上下文上限时，
由模型或上游供应商返回错误，系统沿用请求失败后的现有处理流程，不在 core 增加额外拦截能力。
如供应商默认开启思考模式而请求未显式携带 `enable_thinking`，需要先统一思考状态识别，
否则当前条件会落入非思考分支。

## 上游同步保护

统一使用：

```bash
./scripts/sync-upstream.sh --merge
```

脚本在合并后依次重新装配 extensions、执行兼容合同检查、运行表达式/模板回归测试、构建前端，
并执行后端表达式与结算映射测试。任一步失败都表示同步尚未完成，不能提交子模块指针。

本地功能尽量保存在 `extensions/`。Core 中只保留通用插槽、表达式变量和真实结算映射；
`git rerere` 负责复用已经人工确认过的冲突解决，但不能替代上述自动测试。

GitHub Actions 的 `Verify upstream compatibility` 工作流会在 `main` 推送和 Pull Request 时
重复执行同一组合同检查。即使没有通过同步脚本提交，远端也能发现计费模板或结算映射回归。
